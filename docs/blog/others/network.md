## tcp

### 三次握手
- 确认双向通道正常（客户端→服务器，服务器→客户端）
- 同步双方的初始序列号（防止旧数据混入新连接）
- 防止已失效的连接请求突然生效

==详细过程==
```ts ts:no-line-numbers :collapsed-lines=5
场景：客户端要连接服务器的80端口

第一次握手 - SYN（同步）：
客户端 → 服务器
标志：SYN=1
序列号：seq=1000（客户端随机选的初始序列号）
含义：我想建立连接，我的起始序列号是1000

客户端状态：SYN_SENT（等待服务器确认）


第二次握手 - SYN+ACK：
服务器 → 客户端
标志：SYN=1, ACK=1
序列号：seq=2000（服务器的初始序列号）
确认号：ack=1001（确认收到客户端的1000，期待下一个是1001）
含义：我同意连接，我的起始序列号是2000，我收到了你的1000

服务器状态：SYN_RCVD（半连接状态）


第三次握手 - ACK：
客户端 → 服务器
标志：ACK=1
序列号：seq=1001
确认号：ack=2001（确认收到服务器的2000）
含义：我收到了你的确认，连接建立

双方状态：ESTABLISHED（连接建立）
```

:::important 两次握手会如何 
场景：旧的SYN包延迟到达

1. 客户端发SYN（seq=100）
2. 这个包在网络中延迟了
3. 客户端超时，重发新SYN（seq=200）
4. 新SYN到达，服务器回复SYN+ACK，连接正常建立和关闭
5. 旧SYN（seq=100）延迟后到达服务器
6. 服务器误以为是新连接请求，回SYN+ACK
7. 如果只有两次握手，连接就建立了！
8. 但客户端根本不知道这个连接
9. 服务器资源被无效连接占用
:::

:::tip 三次握手如何避免
第7步后：
1. 客户端收到服务器的SYN+ACK（针对seq=100）
2. 客户端发现："我没发过seq=100的请求啊！"
3. 客户端发送RST（复位）包，拒绝连接
4. 服务器释放资源
:::


### 四次挥手
:::important 
- 四次挥手是因为TCP是全双工通信，两个方向需要独立关闭
- **三次挥手**后服务器可能还有数据要发，不可强制结束
:::

==详细过程==
```ts ts:no-line-numbers :collapsed-lines=5
场景：客户端要关闭连接

第一次挥手 - FIN：
客户端 → 服务器
标志：FIN=1
序列号：seq=5000
含义：我的数据发送完了，准备关闭发送通道

客户端状态：FIN_WAIT_1（等待服务器确认）
客户端：还能接收数据，但不再发送


第二次挥手 - ACK：
服务器 → 客户端
标志：ACK=1
确认号：ack=5001
含义：我知道你要关闭了，但我可能还有数据要发

服务器状态：CLOSE_WAIT（等待应用层关闭）
客户端状态：FIN_WAIT_2（等待服务器发FIN）

关键：此时服务器→客户端方向还开着！
服务器可以继续发送数据，客户端必须接收


第三次挥手 - FIN：
服务器 → 客户端
标志：FIN=1
序列号：seq=6000
含义：我的数据也发完了，可以关闭了

服务器状态：LAST_ACK（等待最后确认）


第四次挥手 - ACK：
客户端 → 服务器
标志：ACK=1
确认号：ack=6001
含义：好的，确认关闭

客户端状态：TIME_WAIT（等待2MSL，确保ACK送达）
服务器收到后：CLOSED
客户端等待后：CLOSED
```
